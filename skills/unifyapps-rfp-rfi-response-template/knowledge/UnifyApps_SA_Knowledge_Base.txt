# 3. Strategic Positioning

## 3.1 Digital Era to Cognitive Era

UnifyApps should be positioned as helping enterprises move from the Digital Era to the Cognitive Era.

The Digital Era created many applications, but also created operational fragmentation.

The Cognitive Era requires a new layer above enterprise systems that can understand context, reason over work, and execute governed actions.

## 3.2 The App Trap

The App Trap describes the situation where organizations keep adding more applications, but business work becomes more fragmented.

The App Trap creates three major problems:

## Data Trap

Business knowledge is scattered across:

- ERP
- CRM
- HCM
- SCM
- Emails
- Documents
- Spreadsheets
- Portals
- Legacy applications
- Databases

Result:

- No unified business context
- Manual search
- Repeated data entry
- Poor decision quality
- Inconsistent customer or employee experience

## Action Trap

Humans become the integration layer between systems.

Employees manually:

- Copy data between applications
- Check multiple portals
- Send follow-up emails
- Update statuses
- Prepare reports
- Escalate exceptions
- Reconcile information
- Trigger approvals

Result:

- Slow cycle times
- High manual effort
- Operational bottlenecks
- Increased error rates

## Governance Trap

Controls are fragmented across systems.

Common issues:

- No single audit trail
- Inconsistent approval rules
- Hard-to-monitor AI decisions
- Limited visibility into tool execution
- Unclear ownership of exceptions
- Difficult compliance reporting

Result:

- Higher operational risk
- Weak control visibility
- Poor auditability
- Limited trust in automation and AI

# 4. Cognitive OS / Smart Worker Positioning

UnifyApps can be positioned as a Cognitive OS or Smart Worker layer above enterprise systems.

This layer does not necessarily replace existing core systems. Instead, it connects to them, understands their data, orchestrates work across them, and enables governed AI-assisted execution.

The platform helps users move from being system operators to business governors.

## Traditional Digital Era User

The user acts as an operator:

- Opens many systems
- Searches manually
- Copies data
- Checks policies
- Follows up by email
- Updates records
- Creates reports manually

## Cognitive Era User

The user acts as a governor or strategist:

- Reviews AI-prepared context
- Approves decisions
- Handles exceptions
- Monitors outcomes
- Adjusts policies
- Improves process performance

# 10. Standard AI Agent Topic Example

## Topic Name

Classify Incoming Request

## Objective

Classify the incoming request into the correct business category and route it to the appropriate workflow.

## Trigger Examples

- "Classify this claim."
- "What type of request is this?"
- "Route this customer email."
- "Analyze this incoming document."

## Step-by-Step Instructions

1. Read the incoming request, email, document, or case description.
2. Identify the main business intent.
3. Match the request to the available categories.
4. Extract key fields required for routing.
5. Check for missing mandatory information.
6. Assign a confidence score.
7. If confidence is below threshold, route to human review.
8. Return the classification, extracted fields, confidence score, and recommended next action.

## Required Inputs

- Request text
- Customer or transaction ID if available
- Attached documents if available
- Available classification categories

## Actions / Tools

- Read source record
- Read attachment
- Query customer or transaction data
- Create or update case
- Route to queue

## Output Format

| Field | Value |
|---|---|
| Classification | |
| Confidence Score | |
| Extracted Fields | |
| Missing Information | |
| Recommended Next Action | |
| Escalation Required | |

## Escalation Rules

Escalate when:

- Confidence is below threshold
- Mandatory information is missing
- Request is high-risk
- Customer is VIP
- Compliance-sensitive data is detected
- The required action is outside agent authority

## Guardrails

- Do not make final regulated decisions.
- Do not execute irreversible actions without approval.
- Do not expose data outside the user's role permissions.
- Always log reasoning summary and actions.

# 13. Sizing Methodology

## 13.1 Core Principle

Sizing is driven by business event volumes, not by user counts.

Users may inform concurrency and capacity assumptions, but they should not drive workflow action or AI session volume.

## 13.2 Default SKUs

Use the following unless instructed otherwise:

| SKU | Usage |
|---|---|
| Unify Applications | Logical applications or business apps |
| Workflow Actions | Executed workflow/system actions |
| Agentic AI Sessions - BYO LLM | AI reasoning sessions using customer-provided LLM |
| Data Pipelines | Required when data ingestion/synchronization is in scope |
| Golden Records | Required when master data/entity resolution is in scope |

Do not include by default:

- Internal User SKU charges
- External User SKU charges
- AI Session Credit - LLM Included

## 13.3 Default Rates

| Item | Default |
|---|---:|
| Workflow Action Credit Rate | 0.01 credits/action |
| AI Sessions | BYO LLM only |
| User SKUs | Not charged by default |

## 13.4 Workflow Action Counting

Count executed actions such as:

- API read
- API write
- Database read
- Database write
- Status update
- Notification
- Approval task creation
- Email send
- Case creation

- Integration call
- Report generation
- Data sync action

Do not count:

- Static page view
- Button click
- UI navigation
- Conditional logic
- Branch logic
- Loop definition
- Displaying already-loaded information

# 18. Standard Customer-Facing Assumptions

Use these assumptions where relevant.

## 18.1 Platform Assumptions

- UnifyApps will provide the application, automation, integration, and agentic AI orchestration layer.
- Customer systems remain the systems of record.
- Customer provides access to required systems, APIs, files, and data sources.
- Customer provides required business rules, policies, and process owners.
- Customer validates workflows, outputs, and acceptance criteria.

## 18.2 LLM Assumptions

- Customer provides the approved LLM unless otherwise agreed.
- LLM cost is excluded from UnifyApps platform credit sizing unless explicitly requested.
- AI output is used as decision support unless explicitly approved for automation.
- High-impact decisions require human approval.

## 18.3 Data Assumptions

- Data quality, completeness, and availability affect automation and AI accuracy.
- Historical data migration is excluded unless explicitly scoped.
- Data cleansing is excluded unless explicitly scoped.
- Document quality affects extraction accuracy.

## 18.4 Integration Assumptions

- APIs or integration methods are available for required systems.
- Customer provides sandbox and production access.
- Customer provides credentials and technical documentation.
- Customer security and network approvals are completed in time.

## 18.5 Security Assumptions

- Customer identity provider will be used where SSO is required.
- RBAC will be configured based on customer roles.
- Audit logs will be enabled for key user, workflow, and agent actions.
- Deployment model and data residency must be confirmed.
